# PRD：互联网资产与漏洞测绘平台（MVP）

> 代号 Atlas（目录 `d:/myself/scan/atlas/`，可改名）。本文档基于已确认的背景约束与 MVP 范围。

## 1. 引言 / 概述

Atlas 是一个面向**互联网资产**的、从零重写的资产与漏洞测绘平台，技术栈为 **Go**。它解决的核心问题是：安全团队需要对自己**拥有或已授权**的互联网资产进行持续、可审计的端口/服务暴露面测绘，并基于资产自动触发漏洞验证，从而在攻击者之前发现风险。

平台主体由两条引擎闭环构成（沿用巡风"资产+漏洞双引擎"思想，但用 Go 重写并去除内网假设）：
- **资产测绘引擎**：对黑名单外的资产进行主动端口扫描、HTTP 探测与指纹识别，建立资产模型并持久化。
- **漏洞检测引擎**：以鲲鹏式（Kunpeng）POC 框架为核心，对资产进行"仅验证、不利用"的漏洞检测。

MVP 不包含任何被动数据源（CT 日志 / DNS / 情报 API），纯主动；不包含 K8s 微服务拆分；不对接既有 CMDB（无）。

**合规底线**：互联网资产扫描受法律严格约束。平台必须内置**可编辑的黑名单**，扫描时排除黑名单内资产、对其余目标发起扫描，并提供**可手动配置的限速**与**可开关的审计日志**。

> ⚠️ 合规提示：本平台已确认**允许对任意目标扫描**，黑名单仅作拦截（即"默认放行"）。运营方须自行确保对扫描目标拥有合法授权。因此部署文档与产品界面须**强制展示法律警示**，明确提示：未经授权扫描第三方资产可能违反《网络安全法》等法律法规。限速与审计均为运营方可配置项（见 OQ-7）。

## 2. 目标（Goals）

- G-1：支持对黑名单外的互联网目标（IP / 网段 / 域名）进行主动端口探测（多模式：TCP Connect / SYN / UDP 等）与 HTTP 探测。
- G-2：通过可热更新的规则引擎完成服务 / 组件 / 版本 / CMS 指纹识别。
- G-3：建立统一资产模型并持久化到 PostgreSQL，支持 ES 全文检索与 Web 控制台检索。
- G-4：内置鲲鹏式 Go POC 框架，支持 JSON 插件与带外（aider）辅助验证，坚持"仅验证不利用"。
- G-5：基于 NATS 任务队列 + Worker 池的调度中心，支持单次 / 周期任务、断点续扫、优先级。
- G-6：在"单机二进制"部署形态下，通过多实例 + 共享队列实现向十万~百万级 IP 的横向扩展。
- G-7：可编辑黑名单 + 扫描时排除 + 可手动配置的限速 + 可开关审计，满足互联网合规要求（允许对任意目标扫描，须强制展示法律警示）。

## 3. 用户故事（User Stories）

### US-001: 维护可编辑黑名单（手动录入）
**描述：** 作为安全运营人员，我希望在 Web 控制台手动维护可编辑的黑名单（IP / 网段 / 域名，即"不扫描的资产"），以便平台扫描黑名单外的一切目标、仅排除这些资产。

**验收标准：**
- [ ] Web 表单支持录入单个 IP、CIDR 网段、域名三种类型，并标明类型
- [ ] 录入后目标出现在"黑名单列表"，显示类型、值、录入人、时间
- [ ] 重复录入同值目标时提示已存在，不重复写入
- [ ] 类型检查与 lint 通过
- [ ] 在浏览器中验证（如通过 run 技能）

### US-002: 批量导入黑名单
**描述：** 作为安全运营人员，我希望通过文件（txt/csv）或 API 批量导入黑名单条目（即"不扫描的资产"），以便需排除的资产清单可快速入库。

**验收标准：**
- [ ] Web 提供文件导入入口，接受每行一个目标的 txt/csv，自动识别 IP/网段/域名
- [ ] 提供 `POST /api/v1/blacklist/import` 接口，请求体为 JSON 目标数组，返回导入成功/失败计数
- [ ] 导入失败时返回逐条错误（行号 + 原因），合法行仍成功入库
- [ ] 类型检查与 lint 通过
- [ ] 在浏览器中验证（如通过 run 技能，文件导入）

### US-003: 扫描时按黑名单排除
**描述：** 作为平台，我希望在派发扫描任务时排除黑名单内目标，以便仅黑名单外的资产被实际扫描，黑名单内资产绝不被触达。

**验收标准：**
- [ ] 调度器在派发扫描任务前用黑名单排除目标集合，仅黑名单外的目标进入扫描队列
- [ ] 被排除（命中黑名单）的目标记录到审计日志（操作人、时间、目标、动作=excluded）
- [ ] 任务其余黑名单外目标正常执行，不因部分目标被排除而整体失败
- [ ] 类型检查与 lint 通过

### US-004: 可手动配置的全局与任务级限速
**描述：** 作为合规管理员，我希望手动配置全局与每任务扫描速率上限，以便扫描行为可按运营需要调速、不危及目标或触发法律风险。

**验收标准：**
- [ ] 系统提供可手动配置的全局限速（最大并发连接数、每目标每秒请求数），无强制默认值，由部署者设定
- [ ] 创建任务时可覆盖限速参数，且不得超过全局配置上限
- [ ] 超过速率时请求进入排队而非失败
- [ ] 类型检查与 lint 通过

### US-005: 可开关的审计日志
**描述：** 作为合规审计员，我希望审计日志可作为开关启用，以便在不需要时关闭记录、需要时追溯谁在何时扫描了什么。

**验收标准：**
- [ ] 提供审计开关配置项（启用 / 禁用）
- [ ] 审计启用时，每次任务创建、任务启动、单个目标扫描开始/结束均写入审计表（操作人、时间、目标、任务ID、动作）
- [ ] 审计禁用时，系统不写入任何审计记录
- [ ] 提供 `GET /api/v1/audit?task_id=` 查询接口，按任务返回审计记录（禁用时为空）
- [ ] 类型检查与 lint 通过

### US-006: 创建单次扫描任务
**描述：** 作为安全运营人员，我希望针对黑名单外资产创建一次性扫描任务，以便立即发起一轮测绘。

**验收标准：**
- [ ] Web / API 创建任务时选择"单次"模式，指定目标范围（引用黑名单或子集）
- [ ] 任务创建后状态为 `pending`，进入调度队列
- [ ] 返回任务 ID，可凭此查询进度
- [ ] 类型检查与 lint 通过
- [ ] 在浏览器中验证（如通过 run 技能）

### US-007: 创建周期扫描任务
**描述：** 作为安全运营人员，我希望创建按周期自动执行的扫描任务，以便资产暴露面被持续监控。

**验收标准：**
- [ ] 任务支持 `cron` 表达式或"每 N 天/小时"周期配置
- [ ] 到点自动生成子任务并进入调度队列，不影响历史任务记录
- [ ] 任务列表区分"单次 / 周期"类型并展示下次执行时间
- [ ] 类型检查与 lint 通过
- [ ] 在浏览器中验证（如通过 run 技能）

### US-008: 端口探测（多模式可配置）
**描述：** 作为扫描引擎，我希望在端口探测时可选探测模式，以便在不同网络环境与主机权限下灵活选择最合适的扫描方式（全连接 / 半开放 / UDP / 隐蔽等）。

**验收标准：**
- [ ] 任务创建或全局配置可指定探测模式（scan_mode），至少支持：TCP Connect（全连接）、TCP SYN（半开放）、TCP FIN / NULL / Xmas（隐蔽）、UDP、TCP ACK（防火墙规则探测）
- [ ] 默认为 TCP Connect（无需特权即可运行）；其他模式可在任务中显式选择
- [ ] 任务可配置端口扫描范围（port_range），支持：常用端口集合（如 Top 1000）、指定端口列表、指定端口区间、全端口（1..65535），默认常用端口集合
- [ ] 按配置范围异步探测，开放端口记录 port + proto + banner
- [ ] SYN / UDP / 隐蔽等需 raw socket 的模式在支持环境（Linux + libpcap）下可用；不支持时回退到 TCP Connect 并给出提示
- [ ] 连接超时由限速配置控制（默认 ≤ 2s）
- [ ] 单 IP 探测在并发上限内完成，不突破全局限速
- [ ] 探测结果写入资产库（open_ports、banner、proto 字段）
- [ ] 类型检查与 lint 通过

### US-009: HTTP 探测（仅针对识别为 HTTP 的服务）
**描述：** 作为扫描引擎，我希望仅对指纹识别为 HTTP/HTTPS 服务的端口发起 HTTP 请求，以便获取标题、响应头、状态码、Cookie、body 等信号，供指纹引擎（参考 WhatWeb / wappalyzergo / CMSeeK）进一步识别 CMS / 组件 / 技术栈。

**验收标准：**
- [ ] HTTP 探测在端口探测与指纹识别（US-010）之后执行，以指纹的 service 字段为门控
- [ ] 仅对 service 字段为 http/https 的端口发起 GET，支持 http/https 两种协议
- [ ] 对服务未识别、但属于常见 Web 端口（80/443/8080/8000/8443 等）的端口，作为补充策略可尝试探测（默认开启、可关闭）
- [ ] 抓取 title、响应头、状态码、body（截断至上限，如 256KB）
- [ ] 支持 gzip 解压与基础 charset 识别
- [ ] 结果写入资产的 webinfo（title 等）
- [ ] 类型检查与 lint 通过

### US-010: 指纹识别规则引擎（可热更）
**描述：** 作为指纹维护者，我希望用正则 / 关键字规则识别服务、组件、版本、CMS（识别维度与签名思路参考 WhatWeb / wappalyzergo / CMSeeK），以便资产自动打标且规则可不停机更新。

**验收标准：**
- [ ] 规则以结构化文件（yaml/json）组织，分 `service / component / version / cms` 维度
- [ ] 规则支持匹配 banner、响应头、body、title 等字段
- [ ] 指纹维度参考 WhatWeb / wappalyzergo / CMSeeK：HTTP 响应头、Set-Cookie、body 特征、`<meta generator>`、特定路径/文件、TLS 证书等，覆盖 CMS / 组件 / 技术栈 / 版本
- [ ] 优先集成 wappalyzergo（Go 原生库）复用其签名集；自研/补充规则以结构化文件管理并支持热加载
- [ ] 提供热加载接口（或文件 watch），更新规则后无需重启即生效
- [ ] 识别结果写入资产的服务 / 组件 / 版本 / tag
- [ ] 类型检查与 lint 通过

### US-011: 资产建模与持久化（PostgreSQL）
**描述：** 作为平台，我希望将扫描结果落成统一资产模型存入 PostgreSQL，以便资产可被检索与关联。

**验收标准：**

- [ ] 同一 `(ip, port)` 重复出现时更新 `last_seen` 与字段，而非新增记录
- [ ] 提供数据库迁移脚本（如 golang-migrate），首次启动自动建表
- [ ] 类型检查与 lint 通过

## 4. 功能需求（Functional Requirements）

- FR-1：系统必须维护一个可编辑的黑名单，支持 IP、CIDR、域名三种类型，支持手动录入（US-001）与文件/API 批量导入（US-002）。
- FR-2：系统必须在派发前按黑名单过滤扫描目标，仅扫描黑名单外的目标，并将被排除的目标记入审计（US-003）。
- FR-3：系统必须提供可手动配置的全局与任务级限速（最大并发连接数、每目标每秒请求数），超限请求进入排队；无强制默认值，由运营方配置（US-004）。
- FR-4：当审计日志开启（开关）时，系统必须为每次任务创建、任务启动、单目标扫描开始/结束写入审计记录（US-005）。
- FR-5：系统必须支持创建一次性扫描任务与周期扫描任务（cron 或间隔）（US-006、US-007）。
- FR-6：系统必须支持可配置的多模式端口探测（TCP Connect / TCP SYN / TCP FIN·NULL·Xmas / UDP / TCP ACK），默认 TCP Connect；端口扫描范围可配置（常用端口集合 / 指定列表 / 区间 / 全端口 1..65535），默认常用端口集合；超时可配置，记录开放端口、协议与 banner；需 raw socket 的模式在支持环境下可用、否则回退（US-008）。
- FR-7：系统必须仅对指纹识别为 HTTP/HTTPS 服务的端口执行 HTTP 探测（以 US-010 的 service 字段为门控），抓取 title、响应头、状态码与截断后的 body，支持 gzip 解压与 charset 识别；对未识别的常见 Web 端口可补充尝试（默认开启、可关闭）（US-009）。
- FR-8：系统必须提供由结构化文件驱动的指纹规则引擎（service/component/version/cms），匹配 banner/header/body/title，并支持热加载（US-010）。
- FR-9：系统必须将资产模型（Host/Port/Domain/Cert）持久化到 PostgreSQL，按 (ip, port) 冲突更新并保留 first/last seen（US-011）。
- FR-10：系统必须将资产索引到 Elasticsearch，支持 `ip/port/server/title/tag/banner/hostname/all` 检索键，banner 含中文走正则、否则走全文检索（US-012）。
- FR-11：系统必须提供 Web 控制台，列出资产并支持检索/翻页，详情页展示端口、指纹、HTTP 信息与关联漏洞（US-013）。
- FR-12：系统必须提供 Go 原生 POC 框架，暴露 `Check(task)` 接口，支持多协议（http / dns / tcp）请求与模板化检测，仅做验证、绝不利用，返回结构化结果（US-014）。
- FR-13：系统必须支持声明式检测模板（参考 nuclei：含 request（http/dns/tcp 等协议）+ matchers（word/regex/binary/status/size）+ extractors），并通过 `GetPlugins()` 列出（US-015）。
- FR-14：系统必须支持 DNS/HTTP 带外辅助验证（aider）（US-016）。
- FR-15：系统必须支持按"全部资产 / 检索条件筛选 / 指定目标"范围发起漏洞检测任务，选择插件集，在限速下调度（US-017）。
- FR-16：系统必须存储带生命周期状态（open/fixed/recur）的漏洞结果，并按 (asset_ref, kpid) 去重（US-018）。
- FR-17：系统必须提供按等级排序的漏洞列表，支持筛选与 Excel/CSV 导出（US-019）。
- FR-18：系统必须使用 NATS 任务队列 + Worker 池调度，进度持久化（可恢复）、支持优先级与多实例共享扩展（US-020）。
- FR-19：系统必须保留资产变更快照并提供按时间对比的接口（US-021）。
- FR-20：系统必须提供 `Dockerfile` 与 `docker-compose`，编排多实例共享同一 NATS / PostgreSQL / ES，便于横向扩展（OQ-6）。

## 5. 非目标（Non-Goals / 本期不做）

- 被动数据源：CT 证书透明度日志、DNS 数据集、FOFA/Shodan/ZoomEye 等情报 API（放二期）。
- 归属关联图 / 拓扑大屏 / 态势可视化（二期）。
- K8s 微服务拆分与独立服务发现组件（本期为单机二进制 + 多实例共享队列）。
- 多租户 / 细粒度 RBAC（本期单管理员 + 操作人字段即可）。
- 对接既有 CMDB / 资产来源（用户明确无）。
- 漏洞利用 / 攻击载荷执行（坚持仅验证）。
- 漏洞生命周期自动修复、工单系统对接（仅状态跟踪，不自动处置）。

## 6. 设计考量（Design Considerations）

- **UI/UX**：控制台三大模块——资产检索、任务管理、漏洞报表。检索框复用巡风式 `key:value` 语法降低学习成本。
- **可复用资产**：指纹识别规则可参考巡风 `Discern_*` 配置与鲲鹏 JSON 插件格式进行迁移，但改为结构化热加载文件。
- **安全边界**：漏洞引擎进程/插件沙箱化，禁止任何写操作与利用载荷；代码评审强制检查。

## 7. 技术考量（Technical Considerations）

- **语言 / 框架**：Go 1.22+；Web 用 Gin/Echo；HTTP 客户端用 `fasthttp`/`req`；协程池用 `ants`。
- **前端**：Vue 3 + 组件库（Element Plus / Ant Design Vue），通过 REST API 与后端交互（OQ-2）。
- **存储**：PostgreSQL（资产主库 + JSONB）+ Elasticsearch（检索）+ 可选 Prometheus（趋势）。
- **调度**：NATS（可嵌入式运行，亦可外置集群）作为任务队列；Worker 池内置于同一二进制。
- **漏洞引擎**：框架自研（Atlas 内置 `vuln` 模块，纯 Go、非 cgo，单机二进制友好），与资产模型/调度/审计/限速深度集成；**POC 内容迁移复用 Kunpeng**——35 个 JSON 插件端口化为新模板格式，51 个 Go 插件端口化到新框架（MVP 先迁移高危/常用部分）；支持 `hashicorp/go-plugin`（RPC）热加载 Go 插件；运行时受全局限速令牌桶约束；坚持"仅验证不利用 + 带外 aider"安全设计。
- **漏洞检测框架参考 nuclei**：声明式模板采用 nuclei 风格的 YAML 模板（matchers / extractors，支持 http / dns / tcp 多协议），社区模板库 nuclei-templates 的签名可直接复用 / 借鉴；引擎自研内置 Atlas（非调用 nuclei 二进制），坚持仅验证不利用。Kunpeng 的 35 个 JSON 插件转换为该模板格式。
- **部署形态与扩展（关键折中，已确认）**：交付为**单个二进制**，进程内聚合 Scheduler / Worker / Scanner / Fingerprinter / VulnEngine / API。为满足"十万~百万级 IP"规模，扩展方式为**运行多个二进制实例，共享同一 NATS 与 PostgreSQL/ES**；实例间通过共享队列隐式协作，**不引入 K8s 微服务拆分、不引入独立服务发现组件**（轻量替代：NATS 集群或 Redis 做容量协调）。该折中已确认（OQ-1）。
- **合规**：黑名单在调度派发前用于排除目标（命中黑名单直接剔除并记录）；限速在 Worker 层令牌桶实现；审计写独立表。
- **性能**：单实例目标——全端口异步探测吞吐受限于令牌桶；百万级规模通过实例数线性扩展（经验公式：实例数 ≈ 目标IP数 / 单实例日处理IP数）。
- **端口探测模式**：默认 TCP Connect（无需特权，基于 Go 原生 net 即可）；SYN / UDP / FIN·NULL·Xmas / ACK 等需 raw socket 的模式基于 `gopacket` + `libpcap`（Linux）实现，Windows 下自动回退到 TCP Connect 并提示。各模式暴露统一的 `Probe(ip, ports, mode, opts)` 接口，便于扩展与限速接入。
- **Web 指纹识别参考实现**：识别维度与签名思路参考 WhatWeb（插件化 Web 指纹）、wappalyzergo（Go 原生库，可直接集成/复用其签名集）、CMSeeK（CMS 专项识别）。HTTP 探测（US-009）提取的响应头 / Cookie / body / `<meta>` / 特定路径作为签名输入；优先直接集成 wappalyzergo 降低自研成本，自研规则以结构化文件管理并热加载。

## 8. 成功指标（Success Metrics）

- SM-1：黑名单内目标排除率 100%（任何命中黑名单的目标均被 FR-2 在派发前排除）。
- SM-2：单实例在配置限速下稳定完成 ≥ 1,000 IP/天 的全端口测绘；通过 N 实例线性扩展至百万级。
- SM-3：资产检索（ES）在千万级数据下 P95 响应 < 1s。
- SM-4：漏洞检测误报率可通过带外验证（aider）与复验降低，目标复验后误报 < 5%（二期度量）。
- SM-5：进程异常退出后，扫描任务可从断点恢复，不重复已扫目标（FR-18）。

## 9. 待确认问题（Open Questions）

- OQ-1（已决议）：确认采用**单机二进制 + 多实例共享队列**即可满足"百万级"预期，不引入 K8s 编排（Non-Goals 不变）。
- OQ-2（已决议）：前端采用 **Vue 3**，组件库用 **Element Plus**（或 Ant Design Vue，二选一，默认 Element Plus）。
- OQ-3（已决议，含建议默认值 [假设]）：限速为手动配置项。建议默认值——单实例全局最大并发连接数 **500**、每目标请求速率 **10 req/s**（均可在配置中调整）；**MVP 不按资产类型区分限速**（单一全局 + 任务级覆盖），二期可按资产类型/风险等级细分。最终阈值以线上压测为准。
- OQ-4（已决议）：漏洞引擎**框架自研**（Atlas 内置 `vuln` 模块，纯 Go、单机二进制友好、与资产模型/调度/审计/限速深度集成），设计参考 **nuclei**（模板化、多协议、社区模板库），**不再以 cgo `.so` 依赖旧 Kunpeng**；**POC 内容迁移复用 Kunpeng**——35 个 JSON 插件转换为 nuclei 风格的新模板格式，51 个 Go 插件端口化到新框架（MVP 先迁移高危/常用部分）。保留"仅验证不利用 + 带外 aider"安全设计。
- OQ-5（已决议）：MVP 中 Host 的 ASN / Org / Geo 字段先留空，二期通过 WHOIS / ASN / RDAP 等数据源补全（属被动源，本期 Non-Goals）。
- OQ-6（已决议）：MVP 即提供 `Dockerfile` 与 `docker-compose`，便于多实例共享 NATS / PostgreSQL / ES 部署（见 FR-20）。
- OQ-7（已决议）：**允许对任意目标扫描**，黑名单仅作拦截（默认放行）。部署文档与产品界面须**强制展示法律警示**，提示未经授权扫描第三方资产可能违法。限速改为可手动配置（无强制默认），审计日志改为可开关。
