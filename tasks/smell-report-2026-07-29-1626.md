# Atlas 架构坏味道与修复点报告

**项目：** Atlas 互联网资产与漏洞测绘平台  
**范围：** 全项目（126 个仓库文件，56 个 Go 文件，约 6,150 行 Go）  
**日期：** 2026-07-29  
**分析方式：** Claude Code 独立只读审查 + Codex 逐项复核 + smell / WooYun 业务逻辑方法  
**基线：** `main`，`ccb6e2e`

---

## Executive Summary

Atlas 是一个分层较清楚的模块化单体：`cmd/atlas` 负责装配，`server` 暴露管理 API，`task` 编排任务，`scan` / `vuln` 执行探测，PostgreSQL 保存任务与管理数据，Elasticsearch 保存资产。Go 编译器和现有测试没有发现依赖环；项目不是“大泥球”，主要问题集中在故障路径、状态一致性、热更新并发和默认部署安全性。

整体健康度评为 **有风险（Risky）**。确认 4 个 P0：默认凭据与后端服务直接暴露、ES 部分资产写入造成字段丢失、任务创建/分发缺少可靠状态机、黑名单查询失败时放行。它们分别可能导致管理面接管、资产数据被覆盖、任务永久卡住或重复执行、黑名单控制失效。

现有测试全部通过，但关键模块覆盖不足：`server` 3.9%、`task` 12.2%、`scan` 15.5%，且没有覆盖 ES 二次写入、NATS 部分发布、配置并发热更新、进程退出等核心故障场景。这解释了为什么当前测试绿灯仍未暴露这些问题。

## Architectural Style Detected

**风格：** 模块化单体 + 外部消息队列的可水平扩展 Worker。

| 期望 | 实际 | 状态 |
|---|---|---|
| HTTP、编排、探测、存储边界清楚 | 包边界基本清楚，Go 构建无循环依赖 | 良好 |
| PostgreSQL/ES 写入具有清晰一致性语义 | ES 使用全文档替换，任务写入跨多步无事务 | 严重 |
| 多实例任务至少一次/恰好一次语义明确 | 使用普通 NATS 发布，缺少 outbox、重试与 processing 状态 | 严重 |
| 热更新无数据竞争且持久化一致 | Config、Auditor、Limiter 存在无锁共享和部分持久化 | 警告 |
| 默认部署最小暴露、凭据外置 | Compose 暴露 PG/NATS/ES，应用播种默认管理员口令 | 严重 |

## Findings by Priority

### P0 — 必须优先修复

1. 默认管理员凭据与无认证数据服务对宿主机开放。
2. ES `PUT _doc` 全文档替换会清空未携带的资产字段并重置 `first_seen`。
3. 任务创建、消息发布和完成更新没有可靠事务边界，任务可卡住或部分执行。
4. 黑名单读取错误被忽略，保护控制在数据库故障时失效。

### P1 — 应在近期修复

1. 审计开关写入旧值，重启后恢复错误；配置热更新还存在数据竞争。
2. 退出信号没有传播到 HTTP、任务和 TCP 连接。
3. 过滤项和并发 Worker 使任务进度错误或倒退。
4. 会话 Cookie、CORS、登录限速和审计身份可信边界过弱。
5. `max_concurrency` 实际混合了 RPS、Worker 数和固定连接并发三种语义。
6. 每目标限速器永久增长，黑名单按目标反复查询全表。
7. ES 写入失败只记日志，README 描述的 PG 兜底和重试队列已不存在。
8. 漏洞检测只探测六个硬编码 Web 端口。

### P2 — 建议优化

1. 超大 CIDR 的错误被吞掉并退化成非法字符串目标。
2. 多个 API 和存储路径吞掉错误，客户端得到“空结果”或假成功。
3. 正则在请求热路径重复编译，前端首包过大。
4. Docker 前端构建不使用 lockfile，README 与当前实现明显漂移。

## Detailed Findings

### Finding 1: 默认凭据与后端服务直接暴露

- **严重级别：** P0
- **类别：** Security / Configuration
- **位置：** `internal/config/config.go:100`、`internal/config/config.go:158`、`docker-compose.yml:5`、`docker-compose.yml:8`、`docker-compose.yml:20`、`docker-compose.yml:25`、`docker-compose.yml:29`、`docker-compose.yml:52`
- **证据：** 首次启动会播种管理员口令 `admin` 和固定会话密钥；Compose 使用 `postgres/postgres`，对宿主机发布 5432、4222、9200，且 ES 明确关闭安全功能，同时发布两个 Atlas 管理端口。
- **影响：** 按默认 Compose 部署到非隔离主机时，管理面、任务总线和资产数据均暴露在可达网络上。固定会话密钥还意味着不同默认部署共享同一个可预测的会话令牌。
- **根因：** 开发默认值进入了部署默认路径，没有 fail-closed 校验和网络隔离。
- **修复：** 内部服务仅使用 Compose 网络，不发布宿主机端口；凭据通过 secret/env 注入；首次启动生成随机密钥并强制设置管理员口令；检测到默认值时拒绝绑定非 loopback 地址；PG/NATS/ES 分别启用认证与 TLS。

### Finding 2: ES 部分写入实际执行全文档替换

- **严重级别：** P0
- **类别：** Data Consistency
- **位置：** `internal/esasset/esasset.go:19`、`internal/esasset/esasset.go:25`、`internal/store/es.go:74`、`internal/store/es.go:80`、`internal/scan/scan.go:228`
- **证据：** `Asset` 会被转换为仅包含非零字段的 map，随后通过 `PUT /<index>/_doc/<id>` 写入。ES 对该 API 的语义是替换整个 `_source`。`finishHost` 只携带 IP、端口数和时间戳。
- **影响：** 二次扫描可清空已有 `asn`、`org`、`geo`、`os`、证书或 Web 指纹；`first_seen` 每次被当前时间覆盖。端口复扫也可能清空本次未探测到的历史字段。
- **根因：** 代码把“省略零值”误当成 ES 的字段级 merge。
- **修复：** 定义明确的 merge/clear 语义，使用 `_update` + `doc_as_upsert` 或脚本更新；`first_seen` 仅在创建时设置，`last_seen` 每次更新；为显式清空字段设计独立标记。增加“同一资产连续写两次仍保留历史字段”的集成测试。

### Finding 3: 任务生命周期缺少可靠事务和消息状态机

- **严重级别：** P0
- **类别：** Architecture / Data Consistency
- **位置：** `internal/task/task.go:122`、`internal/task/task.go:125`、`internal/task/task.go:156`、`internal/task/task.go:164`、`internal/task/task.go:241`、`internal/task/task.go:257`
- **证据：** 任务主记录和子项逐条写入，没有事务；NATS 发布在循环中途失败会直接返回；panic 虽被 recover，但子项不转为 failed；`MarkItemDone`、进度和状态更新错误全部被忽略。
- **影响：** 可产生没有完整子项的 Running 任务、部分消息已发布而部分未发布、panic 后永久 Pending、实际失败但 API 返回已创建。恢复操作还可能重复执行已发布但未记录的工作。
- **根因：** 数据库状态和消息发布没有 outbox/inbox 协议，子项状态只有 pending/done/filtered，表达不了 processing/failed/retry。
- **修复：** 单事务创建 task + items + outbox；后台发布器带重试并记录发布结果；Worker 原子领取 `pending -> processing`，完成后事务写结果和进度；增加 `failed/attempts/last_error/lease_until`；所有持久化错误必须传播或进入重试。

### Finding 4: 黑名单数据库错误时默认放行

- **严重级别：** P0
- **类别：** Business Logic / Control Bypass
- **位置：** `internal/task/task.go:94`、`internal/task/task.go:96`、`internal/blacklist/blacklist.go:64`
- **证据：** `svc.bl.Match(ctx, t)` 的错误被 `_` 丢弃，只有 `hit == true` 才过滤。PG 超时、连接断开或查询失败都会被解释为“未命中”。
- **影响：** 黑名单作为扫描边界时，恰好在存储故障期间创建的任务会继续执行被禁止目标。
- **根因：** 控制类依赖采用 fail-open 错误策略。
- **修复：** 创建任务时传播错误并整体失败；或者使用带版本的本地只读快照，在快照不可用时拒绝创建任务。补充 PG 故障测试，断言没有任务和子项落库。

### Finding 5: 审计开关持久化旧值

- **严重级别：** P1
- **类别：** Correctness
- **位置：** `internal/server/config.go:79`、`internal/server/config.go:95`、`internal/server/config.go:124`
- **证据：** 请求值只传给 `Auditor.SetEnabled`，没有赋给 `cfg.Audit.Enabled`；随后序列化的仍是旧 `cfg.Audit`。
- **影响：** UI 显示配置更新成功，运行时立即变化，但重启后恢复到旧值；关闭和开启审计都可能出现相反的持久化结果。
- **修复：** 先构建新的完整配置快照并验证，再在一个 DB 事务中持久化 scan/audit，成功后原子发布运行时快照。增加“更新后重新 LoadFromDB”的回归测试。

### Finding 6: 配置、审计和限速热更新存在数据竞争

- **严重级别：** P1
- **类别：** Concurrency / Common Coupling
- **位置：** `internal/server/config.go:58`、`internal/server/config.go:79`、`internal/audit/audit.go:21`、`internal/audit/audit.go:29`、`internal/audit/audit.go:32`、`internal/ratelimit/ratelimit.go:34`、`internal/ratelimit/ratelimit.go:58`
- **证据：** `*config.Config` 被 handler 直接读写；`Auditor.enabled` 无同步；`WaitGlobal` 无锁读取 `global`，而 `SetLimits` 在锁内替换指针。
- **影响：** 并发 GET/PUT 配置可能读到撕裂快照，`go test -race` 在覆盖到这些路径时会报告 race，限速器热更新时行为不可预测。
- **修复：** 使用不可变配置快照 + `atomic.Pointer`，Auditor 使用 `atomic.Bool`，Limiter 使用锁保护读取或在现有 limiter 上安全调用 `SetLimitAt/SetBurstAt`。增加并发热更新 race 测试。

### Finding 7: 优雅关闭和 Context 取消没有贯穿执行链

- **严重级别：** P1
- **类别：** Resource Management
- **位置：** `cmd/atlas/main.go:146`、`cmd/atlas/main.go:153`、`internal/task/task.go:164`、`internal/task/task.go:224`、`internal/scan/probe.go:18`、`internal/scan/scan.go:192`
- **证据：** HTTP 使用阻塞式 `Run` 且未调用 `Shutdown`；进程内任务和 NATS Worker 使用 `context.Background()`；TCP 使用 `net.DialTimeout`；限速等待错误被忽略。
- **影响：** SIGTERM 后新请求和扫描仍可继续，容器只能依靠超时强制终止；在途任务可能留下不一致状态。
- **修复：** `signal.NotifyContext` 创建根 context；`http.Server.Shutdown`；任务服务提供 `Stop/Wait`；使用 `Dialer.DialContext`；每个等待和循环都传播 `ctx.Err()`；定义关机时 processing 子项如何回到 pending。

### Finding 8: 任务进度计算不一致且可并发倒退

- **严重级别：** P1
- **类别：** State Machine / Race Condition
- **位置：** `internal/task/task.go:120`、`internal/task/task.go:147`、`internal/task/task.go:259`、`internal/store/pg.go:310`
- **证据：** `total` 包含 filtered 子项，`done` SQL 只统计 Done；全部过滤时任务直接标记 Done 但进度为 0/N。多个 Worker 又采用“分别 count，再分别 update”的非原子流程，较早的计数可能晚写回并让进度倒退。
- **影响：** 前端可显示 Done 但 0%，并发完成时进度短暂或永久回退。
- **修复：** 明确 `completed = done + filtered + terminal_failed`；在单条 SQL 或事务内由数据库计算并更新进度/最终状态；前端展示 filtered/failed 分项。

### Finding 9: 会话与审计身份边界过弱

- **严重级别：** P1
- **类别：** Authentication / Audit Integrity
- **位置：** `internal/server/auth.go:15`、`internal/server/auth.go:22`、`internal/server/auth.go:74`、`internal/server/auth.go:76`、`internal/server/blacklist.go:17`
- **证据：** 所有登录共享 `HMAC(secret, "atlas")` 的长期固定令牌；Cookie `Secure=false` 且未显式设置 SameSite；CORS 反射任意 Origin 并允许凭据；登录没有限速；审计操作者来自客户端可控 `X-Operator`。
- **影响：** 令牌泄漏后在密钥轮换前一直有效，logout 不能服务端失效会话；跨源策略和 Cookie 属性增加管理 API 被滥用的机会；审计记录可伪造操作者。
- **修复：** 使用随机、有过期时间、可撤销的服务端会话；密码存 bcrypt/Argon2 哈希，secret 外置；Cookie 设置 `Secure`、`HttpOnly`、`SameSite=Strict/Lax`；Origin allowlist；登录按 IP 限速；审计身份从认证上下文生成。

### Finding 10: `max_concurrency` 名称与实际行为不一致

- **严重级别：** P1
- **类别：** Configuration / Leaky Abstraction
- **位置：** `cmd/atlas/main.go:72`、`cmd/atlas/main.go:106`、`internal/scan/scan.go:49`、`internal/server/config.go:97`
- **证据：** 同一个值同时初始化令牌桶 RPS 和任务 Worker 数；connect 扫描另有固定 `connSem=50`。热更新时只重建令牌桶，不更新任务 Worker 数，Scanner 也继续使用固定 50。
- **影响：** 用户修改“最大并发”后，实际 Worker/连接并发不变，只改变速率；吞吐和资源占用难以预测。
- **修复：** 拆成 `worker_concurrency`、`global_rps`、`connect_concurrency`；分别实现可热更新的 Worker 池、rate limiter 和 semaphore；API 返回实际生效值。

### Finding 11: 限速器和黑名单在大范围任务下放大资源消耗

- **严重级别：** P1
- **类别：** Performance / Resource Leak
- **位置：** `internal/ratelimit/ratelimit.go:39`、`internal/ratelimit/ratelimit.go:44`、`internal/blacklist/blacklist.go:64`、`internal/task/task.go:94`
- **证据：** `perTarget` map 只增不删，旧 limiter 在限速热更新后也不更新；任务展开后每个 target 都重新查询整张黑名单表。
- **影响：** 大 CIDR 会永久留下数万 limiter，并产生数万次重复全表查询。
- **修复：** 任务创建前一次加载/编译黑名单快照；CIDR 使用预解析网段结构；per-target limiter 使用 TTL/LRU 或任务生命周期缓存，并在配置更新时刷新。

### Finding 12: ES 故障会静默丢失资产

- **严重级别：** P1
- **类别：** Reliability / Documentation Drift
- **位置：** `cmd/atlas/main.go:60`、`internal/scan/scan.go:309`、`README.md:27`、`migrations/000010_drop_asset_tables.up.sql:1`
- **证据：** ES 初始化失败只告警，单条写入失败只打印日志；PG 资产表已删除。README 仍声称 PG 是权威层、失败文档进入重试队列并每 30 秒补写。
- **影响：** ES 短暂不可用即可永久丢失扫描结果，运维按 README 预期会误判系统具备兜底能力。
- **修复：** 选择并落实一种策略：本地/PG durable spool + 指数退避重放，或在 ES 不可用时拒绝启动/暂停任务。同步更新架构文档和可观测指标。

### Finding 13: 漏洞检测忽略资产实际开放端口

- **严重级别：** P1
- **类别：** Correctness / Incomplete Behavior
- **位置：** `internal/vuln/engine.go:64`、`internal/vuln/engine.go:67`
- **证据：** 每个目标固定探测 80、8080、8000、8888、443、8443，没有读取 `AssetStore.ListPortsByIP`。
- **影响：** 非标准 Web 端口上的服务永远不会进入模板检测；同时对未开放的六个端口反复产生无效请求。
- **修复：** 从资产层读取已开放端口和 scheme/指纹；允许任务 scope 显式指定端口；固定端口只作为没有资产数据时的可选 fallback。

### Finding 14: 当前迁移锁仍留有首启竞态

- **严重级别：** P1
- **类别：** Concurrency / Migration
- **位置：** `internal/store/pg.go:48`、`internal/store/pg.go:49`、`internal/store/pg.go:52`、`internal/store/pg.go:59`
- **证据：** 当前实现把迁移文件放进事务并使用 `pg_advisory_xact_lock`，方向正确；但 `ensureMigrationsTable` 在 Begin 和加锁之前执行，多实例首次启动仍可并发执行该 DDL。
- **影响：** 该改动降低了普通迁移竞态，却没有完全覆盖首次创建 `schema_migrations` 的同类窗口。
- **修复：** 先 Begin，再获取 advisory lock，再在同一事务中创建迁移表、读取版本和执行迁移；锁 key 用项目命名空间稳定派生，并记录等待日志。

### Finding 15: Scope 与 API 错误处理存在假成功

- **严重级别：** P2
- **类别：** Validation / Error Handling
- **位置：** `internal/scope/scope.go:40`、`internal/scope/scope.go:42`、`internal/server/asset.go:65`、`internal/server/task.go:60`、`internal/server/vuln.go:50`
- **证据：** 超过展开上限的 CIDR 错误被转换为原字符串目标；主机漏洞查询、任务子项查询和模板持久化错误被忽略。
- **影响：** `/0` 等输入可创建随后失败的任务；PG 故障时“无漏洞”“空子项”或“模板创建成功”会误导用户。
- **修复：** `expandOne` 返回 `([]string, error)` 并传播；所有 API 持久化错误返回明确 5xx；必要时将部分结果和 warning 分离。

### Finding 16: 热路径、构建和测试债务

- **严重级别：** P2
- **类别：** Performance / Testing / Build
- **位置：** `internal/vuln/matchers.go:42`、`internal/vuln/matchers.go:88`、`Dockerfile:22`、`Dockerfile:23`、`README.md:24`
- **证据：** matcher/extractor 每次响应都编译正则；Docker 只复制 `package.json` 并执行 `npm install`，没有使用现有 lockfile；前端生产构建主 JS 为 1,089.06 kB（gzip 360.18 kB）；README 仍称非 CGO、Go 1.22+、PG+ES 双存储，而 Docker/`go.mod` 已是 CGO raw build、Go 1.25、ES-only。
- **影响：** 大模板集增加 CPU；镜像构建不可复现；首屏加载偏重；维护者按过时文档做出错误部署判断。
- **修复：** 模板解析时预编译正则并拒绝非法表达式；复制 `package-lock.json` 后 `npm ci`；路由懒加载和 vendor 分包；更新 README；为 auth/config/task/NATS/ES 故障路径补测试。

## Dependency Graph Analysis

## Refactoring Roadmap

### Immediate Actions（本迭代）

1. 收紧 Compose 暴露面，移除默认管理员口令和固定 secret。
2. 修复 ES merge/`first_seen` 语义并加入二次写入集成测试。
3. 黑名单匹配错误改为阻断任务创建。
4. 修复 `cfg.Audit.Enabled` 持久化旧值和共享状态 race。
5. 让 filtered 项进入完成计数，并用原子 SQL 更新进度。

### Short-Term（1–2 个迭代）

1. 引入 task item 的 processing/failed/lease 状态和事务 outbox。
2. 建立根 context、HTTP graceful shutdown、Worker Stop/Wait。
3. 拆分并发与 RPS 配置，修复 per-target limiter 生命周期。
4. 使用黑名单内存快照，消除按目标全表查询。
5. 漏洞引擎改为读取实际开放端口。

### Long-Term（1–3 个月）

1. 明确 ES 故障策略并实现 durable retry spool。
2. 把 `task.Service` 拆为 TaskRepository、Dispatcher、Worker、ProgressUpdater。
3. 建立 NATS/PG/ES 的故障注入测试和容器化集成测试。
4. 完成会话撤销、密码哈希、secret 管理与审计身份绑定。
5. 让文档、Compose 和实际存储架构保持同一来源生成。

## Claude 候选项复核说明

- `UpdateTaskProgress` 的 SQL 参数顺序正确，不列为缺陷。
- “全局限速器每端口双倍消耗”不准确：任务层每个子项消耗一次，connect 路径才按端口继续消耗；真正问题是 RPS/并发职责混用。
- connect 路径没有调用 `persistResult` 不是直接功能错误，因为连接失败不会落库；建议统一路径属于可维护性优化。
- `domain:` 空 ID 的根因是输入校验，已合并到 Scope/API 校验项，不单列。
- 当前 `internal/store/pg.go` 的事务 + advisory lock 改动方向正确，但需要把迁移表创建也纳入锁内。
